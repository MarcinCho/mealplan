# Meal prep Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Cooking sessions with dishes and portions, portion allocation to the week plan, a household freezer, "na mieście" plan entries, session shopping by the week cooked for, pantry deduction when a session is cooked, and a 4-day reminder for unassigned fresh portions.

**Architecture:** New package `internal/mealprep` (sessions, dishes, freezer, portion accounting) over new store tables. Plan entries get a `kind` (`meal`, `prep`, `out`); `prep` entries point at a dish or a freezer item and carry that portion source's recipe, so nutrition works unchanged. Portion counts are computed from rows (never stored as counters), so deleting an allocation returns its portions automatically. Shopping adds each session's dishes to the list of the week the session belongs to; `prep`/`out` entries add nothing. The pantry gets session-level movements next to entry-level ones.

**Tech Stack:** Go 1.26 (`net/http`, `database/sql`, modernc SQLite, pgx Postgres), Vue 3 + Vuetify 3 + Pinia, Vitest.

**Spec:** `docs/superpowers/specs/2026-11-08-nutrition-mealprep-inventory-design.md` (§6, §7; §5.3 for session deduction; §3 for the `plan_entry` rebuild).

## Global Constraints

- Migrations are portable SQL run unchanged on SQLite and Postgres, split on `;` (no `;` inside strings or comments).
- Every store and service test runs on both engines (`MEALPLAN_TEST_DRIVER=postgres` in CI).
- OpenAPI is the contract: every new route is in `api/openapi.yaml` (`TestRoutesMatchOpenAPI`).
- Household is the tenant: every query filters by `household_id`; a foreign id is 404.
- UI copy is Polish; mobile-first (verify at 390 px).
- "porcji na posiłek" is a household setting, default **2**.
- Session default week: session date on Saturday or Sunday → the Monday after; any other day → the Monday of its own week. Changeable per session.
- Reminder: a session whose date is **more than 4 days** before today and that still has remaining fresh portions.
- "Zrobione" on a `prep` entry never touches the pantry; marking a session cooked deducts its dishes (scaled to dish portions), un-cooking restores.
- A session's shopping covers **all** its dish portions in its week's list, regardless of the `from`/`to` day range; a cooked session adds nothing (like a done meal).
- Commits: `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>` trailer.
- Tooling: `.superpowers/bin/dkgo go …`, `.superpowers/bin/dknode npm …` (runs in `web/`); after a web build `touch web/dist/.gitkeep`.

## Review Focus

1. Upgrading a live database with existing plan entries, done entries and their pantry movements: every row survives migration 0007 on both engines.
2. Deleting a plan entry that came from a dish or the freezer puts its portions back (the dish's or freezer item's `remaining` rises by the entry's servings).
3. Raising servings on an existing `prep` entry beyond what is left is rejected (422), while re-saving the same servings is accepted (the entry's own portions count as available).
4. Deleting a recipe used by a session dish, or a session/dish/freezer item that still has allocations, answers 409 `in_use`, never 500.
5. A Sunday session shows on next week's shopping list with all its portions even when the list is generated for Wed–Fri only; marking it cooked removes those rows on regenerate; its allocated entries never add ingredients.
